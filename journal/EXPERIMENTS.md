## aigis

| Id | Target | Metric | Before | After | Gain | Verdict |

**aigis-01** (kept, 2026-11-11). PQMagic turns SM3 into an XOF by hashing counter||input once per 32 output bytes through init/update/final with two copies of the data. For seeds of at most 51 bytes the padded block is constant except for the counter.

- Change: suites/pqmagic_common/port/pqm_sm3.c: sm3_extended_fast and sm3_oneshot for the optimized variant; PQMagic's sm3_extended kept as pqm_sm3_extended_upstream (port/pqm_sm3_extended.c) for the reference variant. Applies to every PQMagic SM3 suite.
- Checked by: fingerprint
- Note: About 5%. Measured in aigis_sig_lowram, whose optimized key generation differs from the reference only by this and by the row-at-a-time matrix, which does not change key generation time (SHAKE variant in the same run: 38277 vs 38282 us). The compression function was the reference one in that run. A build switch (-D PQM_NO_LEAN_SM3=ON) exists to measure the paths alone; that run was not made. Host check: identical outputs with PQMagic's own hash code.

**aigis-02** (kept, 2026-11-11). Aigis-sig keeps the expanded K x L public matrix (30 KB for set 3) on the stack for the whole operation; signing with set 3 needs 110.9 KB, one kilobyte under the largest block the heap can give. Expand one row at a time instead.

- Change: suites/aigis_sig/pqc_suite/aigis_sig_lowram.inc, generated from PQMagic's sign.c (expand_mat restricted to one row; keygen, sign and verify use it); built as suites/aigis_sig_lowram, where it is the opt variant.
- Checked by: fingerprint
- Note: Verification 71836 to 46204 bytes and key generation 68172 to 42556 bytes at unchanged speed. Signing re-expands the rows in every rejection round: 70627 to 126378 us for this test message (set 2 with one round: 35.6 ms either way). Kept as a separate suite because of that trade.

**fndsa-01** (kept, 2026-11-11). Signing is dominated by emulated double-precision arithmetic in the FFT; upstream's emulation works on 64-bit values, which RV32 has to split anyway. Doing addition and multiplication directly on 32-bit halves, and computing x+y and x-y together for each FFT butterfly, should cut instructions.

- Change: suites/fndsa/pqc_suite/fpr_c3.c (new add, mul, combined add/sub), used by a second copy of the signing code in fndsa_sign_c3.c; keygen and verify unchanged
- Checked by: upstream KAT + 20000 random pairs against upstream routines on the device + 1e9 pairs on the host + fingerprint
- Note: Instruction counts: add 197 -> 139, add+sub pair 394 -> 222, mul 103 -> 80. Falcon-1024 sign 623472 -> 490193 us.

**fndsa-02** (kept, 2026-11-11). GCC 14.2 for RV32IMC compiled the masked selects of the new routines into conditional branches on secret operands. Value barriers should keep the selects branch-free.

- Change: value barriers around the masks in fpr_c3.c
- Checked by: disassembly
- Note: Upstream's own fpr_add gets the same branches from this compiler, so the ref variant is not branch-free on this target.

**fndsa-03** (rejected, 2026-11-11). -O3 for the whole library may speed up the FFT and sampler loops.

- Change: compiler option for all c-fn-dsa files
- Checked by: none
- Note: Does not link: the image is 2 KB over the 321 KB a RAM image may occupy.

**fndsa-04** (rejected, 2026-11-11). -O3 for the signing unit only keeps the image within the limit.

- Change: compiler option for fndsa_sign_c3.c only
- Checked by: none
- Note: The unit grew from 32 KB to 60 KB and the image crashed at startup; not investigated, so there is no timing.

**fndsa-05** (kept, 2026-11-11). Verification hashes the message to a point with SHAKE256; the assembly Keccak-f[1600] should show up directly.

- Change: components/prims linked with WHOLE_ARCHIVE so that pqc_keccakf1600_opt is really the assembly version (before this the weak default was linked and opt equalled ref)
- Checked by: kat+fingerprint
- Note: Sign 228481 -> 219469 us, Falcon-1024 verify 8225 -> 6501 us, measured by the integrator.

**hashes-01** (superseded, 2026-11-11). The ESP32-C3 has a SHA accelerator whose chaining value can be loaded, so it can stand in for the SHA-256 compression function; in portable C one compression is about 4400 cycles.

- Change: components/prims/opt/sha256_hw.c: pqc_sha256_compress_opt() loads the chaining value, writes the block, starts, polls the busy flag, reads the result; byte order of the chaining value with __builtin_bswap32
- Checked by: random-inputs
- Note: 966 cycles per call where about 300 were expected. Replaced by hashes-03. Intermediate build; results/hashes.json holds the final state.

**hashes-02** (kept, 2026-11-11). Find where the 966 cycles go before changing anything: time the register traffic and the compression separately, and test what the accelerator does with its registers.

- Change: suites/hashes/pqc_suite/hw_probe.c
- Checked by: n/a
- Note: A measurement, not a change. One register access is 8 to 9 cycles in straight-line code and 14 in a loop; start plus wait is 88 cycles (7 polls); the 16 byte swaps through libgcc were 430 cycles. The message registers keep their contents, single words can be replaced, and the block is copied when the compression starts (overwriting it right after the start changes nothing, 2000 of 2000).

**hashes-03** (kept, 2026-11-11). The cost is register traffic and byte swapping, not the compression. Swap inline, write registers in straight-line code, write the next block while the previous one is compressed, and let the accelerator load the initial value itself when the caller starts a message.

- Change: components/prims/opt/sha256_hw.c, sha256_hw.h
- Checked by: random-inputs+fips180-vectors+fingerprint
- Note: 630 cycles per single-block call against 4422 for the reference. Calls with 16 blocks: 2296 -> 1392 us per 1024 blocks (218 cycles per block, 18 times the reference). Checked on 3000 random chaining values with 1 to 5 blocks at four alignments and 300 random whole messages.

**hashes-04** (rejected, 2026-11-11). If the compression were over within the latency of one register access, the busy poll could be dropped.

- Change: probe only, in suites/hashes/pqc_suite/hw_probe.c
- Checked by: random-inputs
- Note: Reading the result right after the start is wrong every time. The wait stays.

**hashes-05** (kept, 2026-11-11). There is no hardware for SM3. The reference loops over the rounds, rotates each round constant at run time and moves the eight state words every round; on RV32IMC, without a rotate instruction, all of that is avoidable.

- Change: components/prims/opt/sm3_fast.c: rounds unrolled with the state rotating through macro arguments, constants stored rotated, FF and GG in their 4- and 3-operation forms, expansion unrolled
- Checked by: random-inputs+gbt32905-vectors+fingerprint
- Note: 6249 -> 4215 cycles per block (1.48x). 40 instructions per round, the minimum without a rotate instruction, so assembly was not tried. Code 9.4 KB against 1.5 KB. The first measurement showed no change at all (39618 vs 39630): the object was not being linked, the weak default in prims.c was. Fixed project-wide later with WHOLE_ARCHIVE.

**hashes-06** (rejected, 2026-11-11). SHA-512 has no hardware either and dominates SLH-DSA-SHA2 at levels 3 and 5 once SHA-256 is on the accelerator. Write it in C with explicit 32-bit halves, merged rotations and the cached a^b for Maj, so the compiler has less to get wrong.

- Change: components/prims/opt/sha512_rv32.c (removed again)
- Checked by: host test on 20000 random messages + random-inputs on the board
- Note: 83.2 us per block: 2 % better than slhdsa-c's C (84.8) but worse than PQClean's (81.0). The compiler spills about ten values per round, and a load used by the next instruction stalls this CPU. File deleted.

**hashes-07** (superseded, 2026-11-11). The 16 halves of the working variables, the cached a^b and the message word fit in the 28 usable registers if nothing else does. Generate assembly that never spills and places every load two instructions before its use; test the generated instructions in an interpreter before going to the board.

- Change: components/prims/opt/sha512_gen.py -> sha512_rv32imc.S; block passed as bytes
- Checked by: interpreter against Python SHA-512 (200 blocks) + random-inputs on the board
- Note: 71.3 us per block, 11,330 instructions, 1.19x slhdsa-c's C. Ran correctly on the board at the first attempt. Replaced by hashes-08.

**hashes-08** (kept, 2026-11-12). 320 of the 11,330 instructions turn bytes into big-endian words. A caller that builds its block from words (H in SLH-DSA) can skip that for constants, so take the block as native words.

- Change: components/prims/opt/sha512_gen.py, sha512_rv32imc.S: interface changed to (state, 32 native words)
- Checked by: interpreter (200 blocks) + random-inputs on the board (500, 1 to 3 blocks, four alignments)
- Note: 69.2 us per block (11,066 cycles for 11,042 instructions), 1.23x slhdsa-c's C, 1.17x PQClean's. With the conversion from bytes done by the caller: 72.7 us. 14 KB of code. Not behind pqc_prims.h, which has no SHA-512 entry.

**hashes-09** (kept, 2026-11-12). Through sha256() with the optimized backend a one-block message costs 9.4 us, of which the accelerator is under 3: the rest is the byte-wise bookkeeping of the hash interface. A one-shot helper for messages that fit one block avoids it. This is the shape of a step of an LMS chain.

- Change: components/prims/opt/sha256_hw.c, sha256_hw.h: pqc_sha256_hw_short()
- Checked by: random-inputs (messages of 0 to 55 bytes against the reference)
- Note: 3.8 us against 36.7 for the reference hash interface. Offered to the hash-chain suites; not yet used by them.

**hqc-01** (kept, 2026-11-11). HQC-5 produced wrong keys and ciphertexts on the device. The reference BITMASK macro uses 1UL, which is 32 bits on RV32, and HQC-5 shifts by 37.

- Change: override the macro in the suite's unit files; no upstream file changed
- Checked by: official KAT vectors
- Note: Correctness fix, not an optimization. Affects the reference code on any 32-bit target.

**hqc-02** (kept, 2026-11-11). Every product in HQC has one sparse operand (a few dozen set bits). The reference multiplies two dense polynomials with Karatsuba on 64-bit words, which is slow on RV32 and needs a work area of 18n bits. Shifting and XORing the dense operand once per set bit is far less work.

- Change: suites/hqc/pqc_suite/hqc_c3_pke.c with the inner loop in hqc_c3_mul.S
- Checked by: official KAT + fingerprint + constant-time job
- Note: 375K cycles per product. Work area 2n bits instead of 18n. The assembly loop is 1.6x faster than the same loop in C. The secret positions choose memory addresses and shift counts: on this chip the on-device job ct-mul measures identical cycle counts for 24 supports including adversarial ones, but on a CPU with a data cache, or against power analysis, this leaks where the reference does not.

**hqc-03** (kept, 2026-11-11). The reference multiplies in GF(2^8) with table lookups or bit loops; the chip has a fast integer multiplier, so a carry-less product built from integer multiplications followed by a reduction avoids both.

- Change: suites/hqc/pqc_suite/hqc_c3_gf.c
- Checked by: exhaustive comparison with the reference field multiplication
- Note: 1039K -> 206K cycles. No tables.

**hqc-04** (kept, 2026-11-11). The generic sponge absorbs and squeezes byte by byte with 64-bit shifts; working on words should save time on every hash.

- Change: suites/hqc/pqc_suite/hqc_c3_sym.c
- Checked by: kat+fingerprint
- Note: About 10% off each hash call. The same change would help components/prims/fips202.c.

**hqc-05** (kept, 2026-11-11). The Hadamard transform and peak search of the reference decoder can be restructured for a 32-bit core.

- Change: suites/hqc/pqc_suite/hqc_c3_rm.c
- Checked by: random words against the reference (8 rounds on the device, 200000 on the host)
- Note: 648K -> 340K cycles.

**hqc-06** (kept, 2026-11-11). All of the above together.

- Change: opt variant = hqc-02 to hqc-05
- Checked by: official KAT (3 vectors per level on the device, 100 on the host) + fingerprint
- Note: Keygen 276.9 -> 5.52 ms, encaps 553.3 -> 11.46 ms; stack 66.1 -> 20.4 KB for decaps. Measured before the assembly Keccak was linked.

**hqc-07** (partial, 2026-11-11). The reference code needs 132 KB of stack for HQC-3 decapsulation and about 211 KB for HQC-5; a task stack is capped near 115 KB because the heap is split into regions of at most 128 KB.

- Change: HQC-3 reference runs in its own image (suite hqc3ref) on a static stack; HQC-5 reference is verified on the host only
- Checked by: fingerprint
- Note: The optimized HQC-5 needs 61.6 KB and runs on the device.

**hqc-08** (kept, 2026-11-12). HQC hashes with SHAKE and SHA-3; a decapsulation runs about 100 Keccak permutations, so the assembly Keccak-f[1600] should take off a fifth.

- Change: components/prims linked with WHOLE_ARCHIVE so that pqc_keccakf1600_opt is really the assembly version (before this the weak default was linked)
- Checked by: official KAT + fingerprint, independent rerun
- Note: Keygen 5517 -> 4290 us, encaps 11459 -> 9114 us; HQC-5 decaps 112113 -> 95738 us. Measured by the integrator.

**lms-02** (kept, 2026-11-11). A Winternitz step hashes 55 bytes, exactly one SHA-256 block. Build the padded block once per chain and call the compression function, instead of the one-shot hash API for each of 278,000 hashes.

- Change: suites/lms/pqc_suite/lms.c (hash_short, ots_chain), chosen at run time by lms_fast
- Checked by: RFC vectors + fingerprint
- Note: Reference primitives: 6250 -> 4580 cycles per hash. SHAKE256 H5 W4: 5809905 -> 4814568.

**lms-03** (kept, 2026-11-11). SM3 has the block size and padding of SHA-256, so the same code path serves LMS with SM3 (GmSSL's numbering).

- Change: suites/lms/pqc_suite/lms.c (md_init, md_compress, lms_param_init)
- Checked by: GmSSL's HSS-SM3 vector + fingerprint
- Note: before is GmSSL's own lms.c on the same parameter set (suite gmssl_lms, ref), after is this code with the SM3 of components/prims. This code with reference primitives: 11971856.

**lms-04** (superseded, 2026-11-11). The opt variant showed no gain from the assembly Keccak: the optimized primitives were not in the image (weak defaults won).

- Change: linker flags in the suite's CMakeLists.txt; later replaced by WHOLE_ARCHIVE in components/prims
- Checked by: RFC vectors + fingerprint

**lms-05** (kept, 2026-11-11). With the SHA accelerator a compression takes about 90 cycles, so the cost is the register traffic. The accelerator starts from the initial value by itself and holds its output as the bytes the next block needs: read 8 words, write 9 back shifted by three bytes, start. No conversion, nothing through memory.

**slhdsa-01** (kept, 2026-11-11). Every F, PRF, H and T_l of the SHA-2 sets is one SHA-256 compression (or a few) from a chaining value that is fixed for the key. The ESP32-C3 SHA accelerator can start from a loaded chaining value, keeps it in the byte order of the standard, and keeps its message registers between compressions; slhdsa-c's instantiation interface (function pointers per hash) lets a second instantiation replace only the hashes.

- Change: suites/slhdsa/pqc_suite/slh_sha2_c3.c: F, PRF, chain, H and T_l on the accelerator registers; midstate written straight to the H registers, only changed message words written (5 of 16 inside a chain for n = 16), address and padding words tracked in a copy in RAM, only n bytes read back. slh_glue.c: backend switch in front of slhdsa-c's primitives.

- Note: Key generation 130137 -> 8045 us, verification 176721 -> 11954 us. About 280 cycles per hash against 4200 for slhdsa-c's SHA-256 in C. Still the code used for single hashes; slhdsa-02 builds on it. 'after' is from the build of that moment.

**slhdsa-02** (kept, 2026-11-11). The accelerator needs about 80 cycles per compression and copies the block when it starts. While it works on one hash the block of another can be written, so the wait is not idle. The next block of a chain is unknown until its previous step is read back, so advance two independent chains in turn.

- Change: slh_sha2_c3_tmpl.h: wots_pkgen (all chains of a WOTS+ key, two at a time, then T_l), fors_leaf2 (two FORS leaves at a time), wots_chains (the chains of a WOTS+ signature, two slots). third_party/slhdsa-c: three optional members in slh_param_s and three guarded call sites in slh_dsa.c, because per-hash function pointers cannot express this.
- Checked by: acvp-kat+fingerprint+host model of the accelerator
- Note: Key generation 8045 -> 5641 us, verification 11954 -> 10619 us. About 195 cycles per hash in a WOTS+ key. suites/slhdsa/hosttest runs the same code against a register-level model of the accelerator on the build machine, so the logic was tested before each board run.

**slhdsa-03** (kept, 2026-11-11). The two-slot scheduler of the verification chains indexed its slots with a variable, which kept both chain values in memory. Give each slot its own copy of the code so that both stay in registers.
