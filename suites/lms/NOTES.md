# LMS and HSS (RFC 8554, RFC 9858, NIST SP 800-208)

## Where the code comes from

`pqc_suite/lms.c` and `lms.h` were written for this project from RFC 8554
and RFC 9858. Cisco's hash-sigs (https://github.com/cisco/hash-sigs,
BSD-3-Clause) was considered as the base and not used: it covers only the
SHA-256/256 parameter sets, allocates its working key on the heap, and is
about 10,000 lines. Two conventions were taken from it so that keys stay
compatible: the signature randomizer C and the seed and identifier of a lower
HSS tree are derived from the seed with the RFC 8554 Appendix A formula at
indices 0xfffd, 0xfffe and 0xffff.

Test vectors:

- `lms_kat.h` is generated by `gen_kat.py` from the text of RFC 8554
  (Appendix F) and RFC 9858 (Appendix A).
- `lms_kat_sm3.h` holds the HSS-with-SM3 vector of GmSSL's `tests/lmstest.c`
  (Apache-2.0).

## Parameter sets

All of RFC 8554 and RFC 9858: SHA-256/256, SHA-256/192, SHAKE256/256 and
SHAKE256/192, each with W = 1, 2, 4, 8 and heights 5 to 25, and HSS on top.
In addition LMS with SM3 and W = 8 in the numbering GmSSL uses (tree types 5
to 9 with one-time type 14), which verifies GmSSL's vector.

Verification accepts every height. Signing keys are limited by
`LMS_MAX_LAYERS` (3, so height 15); that is a RAM setting, not a limit of the
method.

## Design for a small device

- No heap. A signing key is one `lms_key_t` of about 10.7 KB; the stack stays
  below 3.2 KB.
- The tree is cut into layers of 5 levels. The key keeps the subtree that
  holds the current leaf in every layer (63 nodes each), and for every layer
  but the top one the subtree that comes next. The authentication path of a
  signature is read from those caches.
- The next subtree is built one leaf per signature, so the cost of a
  signature does not jump when a subtree is used up. Per signature: one
  one-time signature, plus one leaf computation per layer below the top.
  A tree of height 5 needs none, height 10 one, height 15 two.
- HSS: when the lower tree is used up, a new one is generated and signed by
  the tree above. That signature is where the time goes (one full lower tree,
  see the maximum of `hss-*/sign`).

## State

The long-term secret of a tree is the seed, the identifier I and the counter
q. `lms_sign()` calls the `persist` callback with the next q before it
returns a signature, so that an application can store the counter durably
first; a counter that goes back means a one-time key is used twice. In the
tests the callback writes to a variable, so the cost of a flash write is not
in the timings. `lms_key_load()` rebuilds the caches for any q from the three
values; that costs as much as key generation, so an application that restarts
often should keep the top-layer cache as well (not implemented).

## What `opt` adds

Both variants run the same code. `ref` sends every hash through the generic
one-shot API (`sha256()`, `shake256()`, `pqc_sm3()`), which sets up a
context, copies the input and pads it for each call. `opt` (`lms_fast = 1`)
uses the fact that every hash on the hot paths has a short input of fixed
length:

- A Winternitz chain step hashes 23 + n bytes, which with its padding is
  exactly one SHA-256 or SM3 block. The block is built once per chain; each
  step writes the step number and the previous output into it and calls the
  compression function. For SHAKE256 the 200-byte state is filled directly
  and permuted once per step.
- Leaf, inner node and secret derivation hashes are built the same way (one
  block, two for an inner node with n = 32).

- On the device, `lms_hw.c` runs the SHA-256 chains on the SHA accelerator of
  the ESP32-C3 through its registers. The accelerator starts each step from
  the SHA-256 initial value by itself and holds its output as the byte string
  the next block needs, so a step reads the n/4 output words, writes them
  back into the message registers shifted by three bytes together with the
  step number, and starts again: 9 register writes and 8 reads for n = 32.
  The constant words of the block are written once per chain. Nothing is
  converted and nothing passes through memory.

Outputs are identical; the RFC vectors are checked in both variants.

`opt` also selects the optimized primitives of `components/prims`: hardware
SHA-256 for the hashes outside the chains, the assembly Keccak, the faster
SM3.

Notes on the table:

- The rows `h5-w8`, `h5-w4` and `m24-h5-w8` were measured with the final
  hardware chain (straight-line code). The other SHA-256 `opt` rows are from
  the version before it, a loop over the output words, which is about 1.3
  times slower per chain step; a new run will lower them accordingly.

- `lms-sha256-m32-h10-w8/ref` was not run: its key generation is 32 times
  that of H5 (347 s). Signing is the one-time signature plus one leaf.
- Signing time varies with the message (the chain lengths depend on the hash
  of the message); the HSS maximum (650 ms in `opt`, 11.2 s in `ref`) is the
  signature that has to generate and sign a new lower tree.
- With W = 1 and W = 2 the chains are 1 and 3 steps long, so the hash that
  derives each chain's secret, which goes through the general hardware
  backend, weighs more; the gain is smaller.
- The SHAKE sets gain from the assembly Keccak, the SM3 set from the faster
  SM3 and the direct chain; neither has a hardware accelerator on this chip.

Where the gain of the SHA-256 sets comes from, key generation of
`lms-sha256-m32-h5-w8` (278,000 hashes):

| Variant | Time | Per hash |
|---|---:|---:|
| `ref`: generic hash calls, C SHA-256 | 10.86 s | 6250 cycles |
| direct single-block hashing, C SHA-256 | 7.96 s | 4580 cycles |
| direct hashing, general hardware SHA-256 backend (`-D LMS_HW_CHAIN=off`) | 1.11 s | 641 cycles |
| direct hashing, chains on the accelerator's registers, as a loop (`-D LMS_HW_CHAIN=loop`) | 0.632 s | 364 cycles |
| the same as straight-line code (`lms_hw.c`, final) | 0.473 s | 272 cycles |

The register-level chain is worth its 0.5 KB: the general backend has to
convert the chaining value to and from host byte order and write all 16
message words for every step.

## Tree heights

Key generation is one leaf per one-time key, and a leaf costs the same at
every height, so the time for taller trees follows from the measurements
(`opt`, SHA-256/256):

| Height | Signatures | W = 8 | W = 4 |
|---|---:|---:|---:|
| 5 | 32 | 0.47 s (measured) | 0.088 s (measured) |
| 10 | 1,024 | about 15 s | about 2.8 s |
| 15 | 32,768 | about 8 minutes | about 1.5 minutes |
| 20 | 1,048,576 | about 4.3 hours | about 48 minutes |
| 25 | 33,554,432 | about 5.7 days | about 26 hours |

Height 10 was measured with the earlier loop version of the hardware chain:
20.2 s (W = 8) and 3.4 s (W = 4), which is 32 times that version's height 5.

With the reference hash the same trees take 23 (W = 8) and 16 (W = 4) times
longer: height 15 with W = 8 would be about 3 hours. HSS with two levels of
height 5 or 10 reaches the same number of signatures for a fraction of the
key generation time, at the price of a signature that is twice as long.

## Tests

- `kat-rfc8554_tc1`, `kat-rfc8554_tc2`, `kat-rfc9858_tc1..4`,
  `kat-gmssl_sm3_hss`: the published signature verifies; a changed signature,
  a changed message and a truncated signature do not.
- `keygen+sign` for the vectors that publish their private key (RFC 8554
  test case 2, RFC 9858 test cases 1 to 3): the seed gives the published
  public key, and signing at the published q with the published randomizer
  gives the published signature byte for byte. RFC 9858 test case 4 has a
  tree of height 20 and is only verified.
- `selftest`: every signature of a key verifies and a changed one does not;
  a key reloaded from (seed, I, q) signs the same bytes as the key that got
  there by signing; a used-up key refuses to sign.
- `extra/h15test.c` (host only): the same for a three-layer key of height 15,
  2200 signatures across two middle-layer boundaries and eight reload points.

## How to run

```
tools/pqc run lms -f /ref/ --idle 400
tools/pqc run lms -f /opt/ --idle 400
tools/pqc run lms -f lms-sha256-m32-h10-w8/opt --idle 900
```

Sets marked heavy in `suite.c` (height 10 with W = 8) only run when named,
because their key generation takes minutes.
